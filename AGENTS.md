## Learned User Preferences

- Scope: SetupPal installs anything that (a) can be installed unattended from the command line (winget silent, npm, pip, cargo, Modrinth/Fabric through its CLI installer, and so on) and (b) passes the Safety Engine. This is not limited to dev tools. If an app is trusted through winget (in the winget community repo with a silent installer), it is installable, including game launchers and apps that ask for a sign-in after install (Steam, Epic, Roblox, Discord, LMMS). Having a GUI is never a reason to refuse. Near-miss package names must ask confirmation ("Did you mean X?"), never silently rename. Broad category requests clarify and offer 2–4 installable same-category options—no Manual card. Only a specifically named out-of-scope item (Microsoft Store-only such as Minecraft Bedrock, vendor-page drivers, no unattended installer, or Safety Engine block) gets a "Manual setup guide" reply: step-by-step instructions plus similar things it can install. The backend gate decides; the model's opinion never does.
- Release bar: SetupPal installs exactly what the user asked for, nothing extra, never recommends or touches what is already installed or unneeded, and Rewind leaves no leftovers. Chat text and the plan card must agree (the card is the plan). Verification expectations and release gates live in `docs/TESTING.md`; product scope is summarized in `README.md` and `SECURITY.md`.
- No placeholders anywhere in the app (chat, History, tests, or canned defaults)—only real data, real AI responses, and actual errors.
- Expose only the three allowlisted Nebius Nemotron models in Settings (Lightning / Super default / Ultra); never arbitrary IDs, DeepSeek, Qwen, Kimi, or NIM.
- The assistant should be unbiased with no predetermined output, and open broad requests by asking what the user wants installed or set up.
- Prefer adaptive install planning: ask only the clarifying questions that are needed, not a fixed info-gathering script; when the user has named what to set up, proceed to a plan rather than over-asking.
- Optimize prompts for a modest (~30-40B) model: plain, best-practice, easy to understand, with occasional light flavor; keep the system prompt ≤350 words; do not over-babysit it.
- Assistant answers should give clear, concrete recommendations of what it can set up.
- Keep conversation/context memory compact to limit tokens while retaining what the user said.
- Account/settings should make API key paste easy and expose practical controls such as context-window viewing.
- Pixel is the only mascot (Mochi, Byte, and the pet selector are removed); Pixel's chat bubbles should be ambiguous and fun, never quoting the user's messages; keep a small set of smooth, reliable animations (not a large fragile set), and keep Pixel fully inside its container with no clipping.
- Prefer a calm decluttered chat UI (light pet vibe): one focal idea per screen, collapse the empty Tasks panel, keep Pixel as the only pet in view, no empty-state recommendation chips (e.g. web/python presets), an animated generating-plan indicator while a plan is being built, live streamed install/terminal progress so runs do not look stalled, and no fake input affordances that look writable but are not.

## Learned Workspace Facts

- The app (SetupPal) is a zero-trust orchestrator with an AI chat window, settings, and the animated Pixel mascot. The target shell is a real Tauri v2 app. Public docs for contributors and release verification are `README.md`, `SECURITY.md`, `CONTRIBUTING.md`, `CHANGELOG.md`, `docs/TESTING.md`, `docs/DEMO.md`, and `docs/UI.md` (this file is the internal agent exception). Keep markdown user/contributor-facing like a normal GitHub repo.
- Automated CLI gate: installs that run unattended and verify from the command line (e.g. `winget list`, `node -v`, `python --version`, `pip show`) pass. The gate lives in `crates/core/src/installability.rs` and judges winget packages by their manifest (installer type and source), not by a name list.
- AI: Nebius Token Factory only, with user-selectable Nemotron models (Lightning, Super default, Ultra) whose IDs come from the Nebius catalog. No silent model fallback; model choice is separate from the Safety Engine. Key handling must be done properly and keys are never written into docs or memory. Optional Tavily is Safety Engine source-domain consensus only—not general chat web search.
- The assistant is expected to have access to the user's PC specs when recommending installs.
- History and other UI surfaces must use real persisted app state, not demo or placeholder content.
- Release verification runs through `scripts/check.ps1` (workspace tests, build, animation/key/offline checks, and the key-free `scripts/persona-tests` deterministic corpus) and must stay green before calling the app release-ready; fuller gates, live corpus, and VM-diff helpers are in `docs/TESTING.md` and `scripts/vm-diff/`. Prefer those over destructive live installs/Rewind on the host during agent work.
